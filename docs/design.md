# Uni-pars: дизайн «ИИ настраивает один раз, дальше парсинг без токенов»

## 1. Принцип

ИИ используется **только на этапе настройки** (и по явному согласию пользователя — при ремонте сломавшегося рецепта).
Результат настройки — **рецепт**: небольшой детерминированный JSON, который локальный движок исполняет по расписанию
в фоне без сети к LLM и без расхода токенов. Уведомление — результат сравнения нового прогона с сохранённым состоянием.

```
НАСТРОЙКА (ИИ, разово)                    ФОН (без ИИ, постоянно)
─────────────────────────                 ───────────────────────────────
URL + «что парсить» (текст/тап по        WorkManager → загрузка → применение
элементу на странице)                     рецепта → валидация → diff с БД →
   ↓                                      правила уведомлений → Notification
очистка DOM + поиск встроенных JSON/XHR       ↓ (если валидация провалилась)
   ↓                                      «Рецепт сломался. Починить с ИИ?»
LLM → рецепт → локальный тест на странице
   ↓
превью результатов → пользователь ОК → сохранить
```

## 2. Рецепт (формат)

```json
{
  "id": "uuid", "name": "Цена iPhone на shop.example",
  "source": {
    "url": "https://shop.example/catalog?q=iphone",
    "fetch": "http | http_json | webview",
    "headers": {}, "cookieProfile": "optional-ref",
    "pagination": {"type": "none|next_link|page_param|scroll", "selector": "a.next", "maxPages": 3}
  },
  "extract": {
    "type": "css | jsonpath | jsonld | regex",
    "itemSelector": "li.product-card",
    "fields": {
      "title": {"selector": "h2", "attr": "text"},
      "price": {"selector": "[itemprop=price]", "attr": "content", "transform": "number"},
      "url":   {"selector": "a", "attr": "href", "transform": "absoluteUrl"}
    },
    "fallbackSelectors": {"price": [".price b", ".cost"]},
    "key": ["url"]
  },
  "validate": {"minItems": 1, "requiredFields": ["title", "price"], "minFilledRatio": 0.9},
  "triggers": [
    {"on": "new_item"},
    {"on": "field_changed", "field": "price"},
    {"on": "threshold", "field": "price", "op": "<", "value": 90000},
    {"on": "item_removed"}
  ],
  "schedule": {"intervalMin": 30, "constraints": {"network": "connected", "batteryNotLow": true}, "quietHours": "23:00-07:00"}
}
```

Слои устойчивости селекторов (в порядке предпочтения, ИИ получает инструкцию выбирать сверху вниз):
1. Встроенный JSON: JSON-LD, microdata/`itemprop`, `__NEXT_DATA__`/`window.__STATE__` — самый стабильный источник.
2. Скрытый JSON-API (XHR), найденный при настройке → фоном обычный HTTP + JSONPath, без HTML и без WebView.
3. Семантические/`data-*`/`aria-*` атрибуты и якоря по тексту-метке («Цена»).
4. CSS по стабильным классам. **Запрещены** `nth-child`, хешированные классы (`css-1x2y3z`, `sc-abc`), абсолютные пути.
5. Для каждого поля — список запасных селекторов, проверяются локально при создании.

## 3. Настройка с ИИ (расход токенов)

1. Страница открывается в WebView (рендерится JS). Одновременно `shouldInterceptRequest` пишет XHR/fetch JSON-ответы (мини-HAR).
2. Пользователь описывает цель текстом и/или **тапает по элементам** на странице (подсветка). Тап → точный DOM-путь
   выбранного блока, это резко уменьшает неоднозначность и контекст для модели.
3. Препроцессор: удаляет `script/style/svg/noscript/iframe`, комментарии, длинные атрибуты, `data:` URI; схлопывает повторяющиеся
   карточки (оставляет 2–3 примера) и сжимает текст. 100–500K токенов сырого HTML → ~3–15K.
4. Один запрос к LLM со структурированным выводом (JSON-схема рецепта): вход — очищенный DOM-фрагмент, цель, список
   найденных JSON-ответов (усечённых), результат тапа. Cookie/токены/заголовки авторизации в запрос **не попадают**.
5. Движок **локально** прогоняет рецепт на реальной странице. Если не прошёл валидацию — до 2 авто-повторов с текстом ошибки.
6. Пользователь видит таблицу превью и подтверждает. Типичная стоимость: 1–3 вызова, ~10–30K входных токенов, ~1–3K выходных
   (копейки на недорогой модели). Дальше 0 токенов.

## 4. Работа в фоне на Android

| Задача | Решение |
|---|---|
| Периодический запуск | `WorkManager` `PeriodicWorkRequest` (минимум 15 мин; переживает перезагрузку, учитывает Doze) |
| Интервал короче 15 мин | `AlarmManager.setExactAndAllowWhileIdle` (+`SCHEDULE_EXACT_ALARM`) → запуск `OneTimeWork`; либо foreground service (с честным индикатором). По умолчанию — не предлагать <15 мин |
| Загрузка | OkHttp в `CoroutineWorker`; **условный GET** (`ETag`/`If-Modified-Since`) + хеш тела: если не изменилось — выходим за миллисекунды |
| Режим `webview` в фоне | WebView требует main-thread и тяжёл. Использовать только когда нет JSON/HTML-варианта; запуск через expedited work / короткий foreground service, таймаут 30–60 с, один WebView на очередь |
| После перезагрузки | WorkManager восстанавливает сам; `BOOT_COMPLETED` для alarm-схем |
| Убийство процесса производителями (Xiaomi, Huawei, Samsung, Oppo…) | Онбординг: запрос исключения из оптимизации батареи (`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, осторожно с политикой Play), инструкции по вендорам, детектор «пропущенных запусков» с предупреждением пользователю |
| Уведомления | Канал на рецепт/тип, `POST_NOTIFICATIONS` (Android 13+), группировка, deep-link на результат, дедупликация, «тихие часы» |
| Нагрузка на сайты | Джиттер ±10–20 %, экспоненциальный backoff при 429/5xx, лимит запросов на домен, соблюдение `robots.txt` как опция, честный User-Agent |

Ограничения новых Android: foreground service типа `dataSync` ограничен по времени (Android 15) — не строить на нём постоянную работу;
основной механизм — короткие периодические задачи.

## 5. Состояние и сравнение (без ИИ)

Room-таблицы: `recipes`, `runs(recipe_id, ts, status, items_count, duration, error)`, `items(recipe_id, key, fields_json, hash, first_seen, last_seen, active)`,
`events(recipe_id, run_id, type, item_key, old, new)`.
Прогон: извлечь → валидировать → сопоставить по `key` → породить события (`new`, `changed`, `removed`, `threshold`) → отфильтровать по триггерам → уведомить.
Первый прогон после создания рецепта — «базовая линия», без уведомлений о каждом элементе.

## 6. Поломки и «самолечение» (токены только по согласию)

Признаки поломки: не выполнена `validate` (0 элементов, поля пустые), резкое изменение структуры (отпечаток тегов контейнера), HTTP 403/captcha-маркеры, редирект на логин.
Поведение: экспоненциальная пауза → уведомление «Рецепт X перестал работать» с кнопкой **«Починить с ИИ»**.
Ремонт: в модель уходят старый рецепт, последний удачный образец данных (эталон) и новый очищенный DOM; результат тестируется локально и
принимается только если эталонные поля снова извлекаются. Опционально — «авто-ремонт» с месячным лимитом токенов.
Отдельно: распознавание антибота (Cloudflare/captcha) → понятное сообщение, а не бесконечные ретраи.

## 7. Архитектура модулей

- `engine` — чистый Kotlin/JVM (Jsoup, JsonPath, kotlinx.serialization): исполнение рецепта, валидация, diff. Тестируется на JVM на сохранённых HTML-снимках.
- `ai` — интерфейс `RecipeGenerator` + адаптеры провайдеров (Claude/OpenAI/Gemini), BYOK-ключ в Android Keystore/`EncryptedSharedPreferences`, лимиты и учёт токенов.
- `capture` — WebView-сессия настройки, выбор элементов, перехват XHR, препроцессор DOM.
- `work` — WorkManager-воркеры, расписание, backoff.
- `data` — Room, репозитории.
- `notify` — каналы, правила, deep-link.
- `app` — Jetpack Compose UI: мастер создания, список рецептов, история, экран «здоровье» (последний успех, ошибки, пропуски).

## 8. Что покрывается, а что нет

| Сценарий | Фон без ИИ |
|---|---|
| Статический HTML, JSON-LD, открытые JSON-API | Отлично, дёшево по батарее |
| SPA без доступного API | Работает через WebView, дороже по батарее, реже |
| Пагинация (ссылка/параметр) | Да |
| Бесконечный скролл | Через API-пагинацию, иначе WebView |
| Логин (cookies в общем CookieManager WebView) | Да, пока сессия жива; протухание → уведомление |
| 2FA/капча/жёсткий антибот | Нет (граница «универсальности») |

## 9. Риски

- Сайты правят вёрстку → ремонт рецептов; смягчение: JSON/API-приоритет, запасные селекторы, понятные уведомления.
- Убийство фоновых процессов производителями → онбординг и детектор пропусков (жёстко решить нельзя).
- Юридическое/ToS/персональные данные → предупреждение при создании рецепта, не обходить защиту.
- Безопасность: ключ не в APK; cookie и токены не отправлять в LLM; рецепты не исполняют произвольный код (только декларативные селекторы/transform из белого списка).
- Политика Google Play по фоновой работе и исключению из оптимизации батареи.

## 10. План

1. **M1 engine**: формат рецепта, исполнитель (CSS/JSONPath/JSON-LD), валидация, diff, тесты на HTML-снимках.
2. **M2 фон**: WorkManager, Room, уведомления, условный GET, backoff — на рецептах, написанных вручную (ИИ ещё не нужен).
3. **M3 настройка с ИИ**: WebView-захват, препроцессор, `RecipeGenerator`, превью, цикл самопроверки.
4. **M4 XHR-режим**: перехват и выбор скрытого API.
5. **M5 ремонт и здоровье**: детекторы поломок, «Починить с ИИ», онбординг по вендорам батареи.
6. **M6 WebView в фоне** для SPA и бета-тест на реальных сайтах.
